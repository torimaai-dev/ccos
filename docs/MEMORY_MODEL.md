# Memory Model

## 目的

このドキュメントは、Captain Chappy（CCOS）がGitHubをAIの外部記憶として使うときの基本モデルを説明します。

CCOSの記憶は、ただの保存場所ではありません。

AIとの対話、作業ルール、判断軸、未決事項、ナレッジを、次の対話や作業で使える形に保つための仕組みです。

## なぜGitHubを使うのか

AIの記憶をGitHub上のファイルとして扱うことで、次の利点があります。

- ユーザーが内容を確認できる
- 必要に応じて編集できる
- 変更履歴を追える
- レビューできる
- 公開用とprivate用を分けられる
- Codexや他のAIセッションに引き継げる
- 壊れたときに戻せる

見えない記憶だけに頼るのではなく、ユーザーが所有できる記憶を作ることが目的です。

## 記憶の種類

CCOSでは、記憶を混ぜずに扱います。

### 1. Public documentation

公開してよい説明やテンプレートです。

例:

- README.md
- docs/
- templates/
- examples/

### 2. Project instructions

AIやCodexが作業するときに読むルールです。

例:

- AGENTS.md
- 作業範囲
- 禁止事項
- レビュー条件
- ファイル配置ルール

### 3. Reusable knowledge

再利用できる知見です。

例:

- 判断軸
- ワークフロー
- プロンプト設計の考え方
- メモ整理ルール
- ユースケース別の型

### 4. Current notes

まだ整理途中のメモです。

例:

- 会話から回収した素材
- 未決事項
- 反映候補
- 後で見直すアイデア

### 5. Private memory

公開してはいけない個人用の記憶です。

例:

- 個人情報
- 非公開の会話ログ
- 本音の作業メモ
- private repository の固有内容
- 公開前の未整理な素材

private memoryは、public repositoryへそのまま移してはいけません。

## 状態ラベル

AIが記憶を扱うとき、状態を取り違えないことが重要です。

CCOSでは、少なくとも次の状態を区別します。

- `draft`: 下書き
- `candidate`: 反映候補
- `accepted`: 採用済み
- `needs_review`: 確認待ち
- `private`: 公開不可
- `archived`: 参照用・通常は更新しない

状態が曖昧なものを、AIが勝手に採用済みにしてはいけません。

## 公開用とprivate用の分離

CCOSでは、公開用リポジトリとprivateリポジトリを分ける運用を想定します。

```text
private repo
  個人の記憶、未整理メモ、実験ログ、非公開情報

public repo
  README、docs、templates、examples、公開できる設計
```

private repoは母艦、public repoはショーケースです。

公開用へ移すときは、次の処理を行います。

1. 個人情報を削る
2. 固有事情を一般化する
3. 再利用できる型にする
4. 状態を確認する
5. レビュー可能な形にする

## メンテナンス

記憶は、保存するだけでは使いにくくなります。

定期的に次の観点で整理します。

- 重複していないか
- 古くなっていないか
- 仮置きと採用済みが混ざっていないか
- private情報がpublicに入っていないか
- 次に使いやすい形になっているか
- READMEやdocsと矛盾していないか

これは、人間の脳が睡眠中に記憶を整理する感覚に近いものです。

## AIが守ること

AIがCCOSの記憶を扱うときは、次を守ります。

- 未確認の内容を採用済みにしない
- private情報をpublicに出さない
- 提案と実行を混ぜない
- ファイルの役割を変えない
- 既存の文脈を弱めない
- 必要に応じてレビュー待ちにする

## 最終目標

最終的な目標は、誰もが自分で所有でき、見直せて、育てられるAI記憶を持てることです。

AIとの対話が、その場限りの会話で終わらず、次に使える知識と作業環境として積み上がる状態を目指します。
